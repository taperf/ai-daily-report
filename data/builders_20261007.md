**Guillermo Rauch (Vercel CEO)**

Rauch launched gdp-ts: "Ghosts of Departed Proofs" for TypeScript — a library, linter and AI skill for safer API design. Under this contract, sensitive functions require compile-time "proofs" that the caller performed an authorization check, so the typechecker can prevent both humans and agents from shipping catastrophic security bugs. His framing is the sharp part: these patterns existed for years in Haskell but stayed niche because of human review cost and syntactic overhead — "the situation is now inverted. Agents are writing more code than we can review, and they thrive in tight loops with hard constraints that would frustrate us." The README models a real Vercel constraint: changing a Project password requires proof of a specific role + entitlement.

Rauch 发布了 gdp-ts：TypeScript 版的"逝去证明的幽灵"——一个集库、linter 和 AI skill 于一体的 API 安全设计工具。在这套契约下，敏感函数要求调用方提供已在编译期验证的"证明"（比如完成过权限检查），由类型检查器拦截人和 agent 交付的重大安全漏洞。最锐利的是他的判断：这套模式在 Haskell 生态存在多年，却因人工审查成本和语法负担始终小众——"现在局面反转了：AI 写的代码已经多到人类审不完，而它们恰恰擅长在那些让我们抓狂的强约束闭环里工作。"README 直接以 Vercel 真实约束建模：修改项目密码需要特定角色+特定授权的证明。这是"AI 时代软件工程范式迁移"的又一实证。

**Aaron Levie (Box CEO)**

Levie's diagnosis of where enterprise agent adoption is actually bottlenecked: testing, tuning and optimizing agents against "real" work environments — the files, CRM systems and email they need to access. You can't know how an agent performs without evals on real work, and every enterprise has to build this 1-by-1 today, which is slow and tedious. His prediction: every enterprise will end up with dedicated staff managing evals and the infrastructure for building and running evals and simulated environments. Huge space.

Levie 点出了企业 agent 落地真正的瓶颈：在"真实"工作环境（agent 需要访问的文件、CRM、邮件等）中测试、调优和优化 agent。不跑真实环境 eval 就无法判断 agent 表现，而现在每家企业都得手工作业、逐个搭建，慢且繁琐。他的判断是：每家企业最终都会配置专人管理 eval，以及构建和运行 eval 与模拟环境的基础设施。这是一个巨大的新市场。与 Madhu Guru 今天的"evals are your product spec"形成有趣共振——工程侧和商业侧在同一天指向同一个词：eval。

**Thariq (Claude Code @ Anthropic)**

Two substantive signals from Claude Code engineering. First, a token-efficiency argument for structured planning artifacts: planning in a compact format beats raw HTML because the model doesn't need to rebuild components or logic for common things like state machines, diagrams and code snippets. Second, his favorite name for a new pattern — "local hands": Claude runs in the cloud but can access your files locally, and it's also coming to Cowork. That's a meaningful architecture shift: compute stays remote, data access stays local.

来自 Claude Code 工程侧的两条实质信号。其一，结构化 planning 工件的 token 效率论证：用紧凑格式做规划优于原始 HTML，因为模型不必为状态机、图表、代码片段这类常见元素反复重建组件和逻辑——这是"agent 界面表示法"的工程细节，很见功力。其二，他给一个新模式起的名字——"local hands"（本地之手）：Claude 在云端运行，却能访问你本地的文件，且该能力即将登陆 Cowork。这是个有分量的架构信号：算力留在云端，数据访问留在本地，等于绕开了 agent 时代数据主权的核心矛盾。

**Madhu Guru (Sr Director, AI at Meta; previously led Gemini, Veo, Nano Banana at Google)**

A crisp product-engineering principle: the most common mistake teams make is treating evals as an additional QA step once the agent is built. "AI products are fundamentally different. Your evals are your product spec." Coming from someone who shipped both Gemini and Nano Banana, this is a compact statement of how AI product development inverts traditional software流程.

一条精炼的产品工程原则：团队最常犯的错误，是把 eval 当作 agent 建成之后追加的 QA 环节。"AI 产品有本质不同——你的 eval 就是你的产品规格书。"出自同时操盘过 Gemini 和 Nano Banana 的人之口，分量不轻。传统软件是先写 spec 再验收，AI 产品则要求 eval 与产品定义同步生长，这个反转值得每个做 AI 产品的人记下来。
